Why

Today the UI is four systems stacked on top of each other

Every screen picks its own button, modal, gray and blue. Nothing is themed to the brand, and some of it is broken in ways users already see.

4

UI layers: shadcn (133 files), MUI (63, default blue), PrimeReact (13, indigo theme), and the V1 kit

3

color systems mixed: ~1,900 brand classes, ~1,970 Tailwind defaults, ~330 raw hex values

302

color classes render nothing (81 files). Spinners don't spin, skeletons don't pulse, gradients are gone

3+

implementations per component. Buttons alone: V1, shadcn, MUI, and 271 raw <button>s

Salvar

Our main button fails contrast: white on #FF7600 is 2.68:1 (AA needs 4.5). It's used 77 times.

ModalTemplate (73 files) isn't an accessible dialog: no role="dialog", no focus trap, and Esc doesn't close it. 4 icon libraries, toasts in the library's default colors, and the shadcn theme is still stock zinc.

Source: UI inventory of origin/develop2

The proposal

A code-first design system, shipped in one PR

🎨 Tokens

Brand colors, type, spacing, radius, shadows and layers as CSS variables + Tailwind. Two layers: raw primitives below, meaningful names (primary, cta, success…) above.

🧩 One component library

shadcn/Radix + cva in components/ui, restyled to the brand. MUI, PrimeReact, headlessui, the V1 kit and 3 icon libraries are retired.

📚 Living catalog + guardrails

Storybook for every component, plus guard tests and jsx-a11y in CI so the codebase can't drift back.

In scope

  • Every screen: public site, student area, admin dashboards
  • Accessibility fixes (contrast, focus, dialogs, labels)
  • Mobile behavior (touch targets, table cards, full-screen dialogs)
  • Writing and accessibility guidelines

Out of scope

  • The Figma library (it can mirror the spec later)
  • Dark-mode values (the structure is ready for them)
  • Chart-library consolidation (colors only)
  • Publishing Storybook (later, when needed)
Code is the source of truth · dashV2's tokens are the seed3

Token architecture

Two layers, all CSS variables

Components and screens
bg-primary text-muted-foreground border-input bg-success-muted
↓ use only
Semantic tokens: shadcn's names, extended
--primary --cta --muted-foreground --success --warning --info --page --highlight
↓ point at
Primitives: CSS variables only, no Tailwind classes
--marine-900 --orange-700 --mint-400 … 8 hues × 11 steps
  • Everything lives in src/styles/tokens.css. Tailwind only maps names to hsl(var(--x) / <alpha>).
  • Themes re-point the same tokens: [data-theme="marine"] on the home page today, .dark later. Components don't change.
  • Toasts, the date picker and charts read the same variables.
  • English names. Semantic names never mention a hue (no --orange-button).
  • Phase 0 fix brings the 302 dead classes, spinners and gradients back to life.

Spacing · radius · elevation · layout

Formalize what the code already does

Spacing

Keep Tailwind's 4px scale. Components use 2–32px, layout 40–96px. Arbitrary p-[48px] is banned.

Radius: one job each

4 · chips6 · controls
8 · cards12 · dialogspills

Borders, not shadows

In-page surfaces get a 1px border. Shadows only for things that float (menus, toasts, dialogs), in 3 marine-tinted levels.

cardmenudialog

Breakpoints stay

sm 768 mobile/desktop split · md 1200 full desktop. Changing them would rewrite ~960 classes. Note: our sm is Tailwind's md.

Layout tokens

Gutters 16/24/32 · widths prose-content 720, form 560, page 1200 · Dialog size 400/560/800 · --header-h replaces 17 magic numbers

Named z-index layers

base · raised · sticky · header · overlay · popover above dialogs · toast. No more z-[1400].

Guidelines

How we write, and how it must work for everyone

✍️ Voice

  • Friendly, with “você”
  • Sentence case
  • Buttons: verb + object (“Excluir prova”, never “OK”)
  • “!” only for celebrations
  • pt-BR dates and numbers

⚠️ Errors

  • What happened + what to do
  • Field errors under the field, never in a toast
  • Blocking errors: inline Alert + retry
  • No codes, no blame

♿ Accessibility

  • AA contrast, 12px min, visible focus
  • Heading order, labelled controls
  • No clickable divs
  • Reduced motion respected
  • jsx-a11y in CI

📱 Mobile

  • 44px targets
  • Single-column forms, sticky action bar
  • Right keyboard (inputMode)
  • Nothing hover-only

Usage rules on one page: one cta per screen · borders vs shadows · dot vs tint badges · prose vs body · one secondary text color · required asterisk · error toasts persist · underline tabs · 12px minimum.

Catalog and guardrails

Storybook to see it, tests to keep it

📚 Storybook 10.6

  • Every ui component has a story for each variant and state (enforced)
  • Autodocs, controls, axe panel
  • Toolbars: 390/768/1200, data-theme
  • MDX: foundations + guidelines
  • The vitrine stays for feature screens

🛡️ Guard test

  • No legacy colors or sizes
  • No arbitrary [#hex], [Npx], z-[N]
  • No banned imports (MUI, PrimeReact…)
  • No new files in the atomic folders
  • No component without stories
  • Strict (zero) from the merge

✅ Also in CI

  • Contrast test: every token pair checked with WCAG math
  • Stories rendered as smoke tests
  • build-storybook on design-system changes
  • ESLint fixed (broken on develop today) + jsx-a11y

Where it lives: components/ui (components + stories) · styles/tokens.css · tailwind/type-scale.js · lib/palette.ts · design-system/ (guards, contrast test, docs) · .storybook/. dashV2's table and badge move into ui, and its list template stays as a consumer.

Migration

One PR, ten ordered commits, each one green

~519 of 1,327 files. Merged without squashing, so any step can be bisected or reverted on its own. Rebase daily, re-run the codemods, then a 2–3 day UI freeze for final QA.

Codemods

A mapping table (old class → token) lives in the spec. Ambiguous cases get /* ds-review */ and are fixed by hand. CI fails until none remain.

Verification

CI · before/after screenshots of every vitrine state at 390 and 1280 · a homologation checklist of key student, admin and public flows.

Scope rule

Parity + the decided improvements only. Bugs found are logged, not fixed. Tests are adapted, never deleted. Rollback = revert a step or the merge.

Risks

What could go wrong, and what we do about it

RiskMitigation
A 519-file PR can't be reviewed line by lineOne theme per commit, codemods reviewed as patterns, screenshot diffs instead of class diffs, ambiguous cases flagged
The branch goes stale (~12 commits/day on develop)Rebase daily, sweeps are re-runnable scripts, short UI freeze only at the end
Behavior regressions (DataGrid → DataTable, modals → Radix)One commit per DataGrid screen, existing tests adapted with their assertions, homologation checklist ★ flows
Users notice every screen changedChanges are deliberate (contrast, focus, mobile); a “what changed” note for cursinho coordinators
Something breaks in productionMerge commit: git revert one step, or the whole merge
Drift after the mergeGuard strict at zero, jsx-a11y as errors, stories required, contrast test
